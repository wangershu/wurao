## 一、先说一个改变顺序的发现：技术栈普查（adb 实测）

设备 56da4a86 上拉了两个目标 App 的 APK 判定：

| | 懂车帝 `com.ss.android.auto` | 美团 `com.sankuai.meituan` 12.44.203 |
|---|---|---|
| Flutter | 无 | 无 |
| Compose | 少量（dex 命中 50） | **无** |
| React Native | 无 | 极少 |
| 自研跨端 | **Lynx 实锤**（`liblynx.so` 3.2MB、`liblynx_v8_bridge.so`、`assets/bdlynx_core.js`） | 无 |
| 广告 SDK | 穿山甲类名搜不到（字节系会重定位） | **优量汇 `com/qq/e/ads`，命中 99 次** |
| 网络栈 | 字节自研（`libtnet`） | Cronet |

**结论（直接影响排期）**：
- **美团是最理想的靶子**：传统 View 树 + 明确广告 SDK → 控件层和 SDK 层都可用，先拿它验证。
- **懂车帝的界面大量走 Lynx**，Lynx 渲染的内容在进程内会塌缩成一个 View —— 控件层对它基本无效。
  → 懂车帝只能靠 L0（请求 / 组件 / SDK 拦截），这正好印证了 L0 不能省。
- 因此 **L0 的优先级上调**，且验证必须包含懂车帝（不能只验美团就宣布成功）。

## 二、菜单方案（沿用上一版三个页签，按新需求调整）

> 上一版结构：底部三个页签（看板 / 应用 / 设置），设置下挂二级页，miuix 风格。这次沿用。

### 页签 1 · 看板
- 顶部一行：框架是否接管（没接管就明说，别让人猜）
- 今天拦了多少（按 App 排序，点进去跳该 App 详情）
- **最近命中记录**（排错主入口）—— 一条记录要能看出：哪个 App、哪条规则、干了什么、什么时候
  → **点记录直接跳到那条规则**，当场停用或删掉（这是你要的"拦截了我某项功能不正常时知道动哪条"）
- 右上角：一键全停（出问题先停，再慢慢查）

### 页签 2 · 应用
- 应用列表（只列被接管的）
- → **应用详情**：
  - 该 App 总开关；**风险级单独一个开关（默认关）**，旁边写清楚"可能让 App 起不来"
  - 规则清单分两栏：
    - **我抓的**（可改可删，优先级最高）
    - **订阅来的**（只能停用 / 删除，不提供编辑）
  - 每条规则一行：一句人话 + 开关 + 最近是否还命中（失效的标黄）+ 命中次数
  - 点进规则详情：定位链、动作、范围、原文 + 这条规则的命中记录 + 停用 / 删除

### 页签 3 · 设置
- **规则源**：订阅（GKD / DNS 域名表）→ 一键重新导入拉最新；导入结果显示"新增多少、覆盖多少、跳过多少"
- **能力开关**：安全级四项 / 风险级三项，每项一句人话说明
- 命中记录与日志：总量、清空、保留策略
- 自检：不用开框架也能验哪些手段有效
- 备份与恢复：规则导出 / 导入
- 关于：含无障碍权限说明（抓控件必须要，不开也能用其它能力）

### 检视层（自抓控件）
入口放在应用详情的"加一条"，以及悬浮球。抓完直接落到这个 App 下。

## 六、风险（开工前先看一遍）

- **R1 懂车帝 Lynx**：控件层对它无效，只能靠 L0；如果 L0 也拿不下懂车帝，要如实说，别硬做。
- **R2 Android 16 兼容性**：每个 hook 点必须"失败也不崩"+ 失败计数上报（见需求第七节第 1 条）。
- **R3 开销 × 进程数**：常驻内存 <500KB/进程，S8 实测。
- **R4 法律**：自用不分发；一旦要发布必须先重开 D4。
- **R5 三层退化成三套**：五域共用一套模型，不许就地开小灶（`risk.md`）。

## 七、大白话：这套东西到底怎么干活

先纠正一处：**原版「悟空」干的是「屏蔽」，不是「点击」**。原版是两套东西配合：

- **悟空**（跑在 App 进程里）：让广告**不发生** —— 广告页不让它打开、广告控件藏掉、广告域名解析到本地。
- **八戒**（无障碍服务）：**替你点**「跳过」—— 站在 App 外面跨进程看控件树，找到了派发一次点击。

我们这版把「点」也搬进了 App 进程里（原版要靠无障碍，我们不用了），所以无障碍能整个关掉。
你那句理解对了一半：**点击确实是进程内 hook 点击；控件这块是用新的选择器引擎达到悟空的效果，
而且比原版表达力强得多**（原版只会「类名+id+文字+往上几层」，新引擎支持兄弟关系、文字长度、
逻辑组合这些）。

三层用大白话说就是：

| 层 | 大白话 | 什么时候起作用 |
|---|---|---|
| **L0 源头断供** | 广告还没出来就掐掉：让广告 SDK 起不来、广告请求发不出去、广告页根本不让打开 | App 启动 / 发起请求那一刻 |
| **L1 看见就认** | 用「所有 App 通用的两条眼力」认出开屏广告，默认全开 | 进页面那一两秒 |
| **L2 你自己指的** | 你指着某块说「这是广告」，它记住，下次自己处理 | 你抓过之后 |

对比原版：原版只有 L0 的一部分（组件/文件/域名）+ 逐条控件规则；
L1「全局规则 + 例外名单」是从 GKD 学来的，**它让规则规模随「误伤」增长，而不是随「应用数」增长** ——
旧规则库停更 21 个月就废了，就是因为这个。

## 八、耗电：预估与硬约束（**你最关心的**）

### 8.1 结论先说

按现在的设计，**耗电量应该在每天 0.05% 以内 —— 24 小时实测大概率测不出来**。
内存反而不必太在意（你说了无所谓，正好，进程内方案的内存本来就小）。

### 8.2 怎么估出来的（量级估算，待实测）

| 项 | 估算 | 依据 |
|---|---|---|
| 一次控件树遍历（500 节点） | 0.3~1 ms | 进程内直接读对象，**没有跨进程调用** |
| 同样的遍历走无障碍 | 10~30 ms | 500 次 Binder，单次 ~50μs（旧实测：一屏 300 节点 = 300 次 IPC） |
| 一次域名查询 | 0.83 μs | 旧实现实测 |
| 一次动作（点一下 / 藏掉） | < 1 ms | — |
| **一次 App 冷启动总开销** | **5~20 ms CPU** | 含一次性规则加载；多数事件在第一道闸就返回（< 10μs） |
| 一天（约 100 次冷启动） | 0.5~2 秒 CPU | — |
| 换算电量 | **0.01~0.03%/天** | 5000mAh≈19Wh，CPU 满载 1 秒量级 0.003%，短任务有唤醒损耗按 3~5 倍系数 |

**对比无障碍方案**：服务要常驻、订阅界面变化事件（滚列表每秒几十次）、每次可能触发一次跨进程遍历。
粗估 0.2~0.6%/天，**比进程内方案高一个数量级**。这就是"能关掉无障碍"真正的价值 —— 不是功能，是电。

### 8.3 真正会让耗电飙高的，不是"匹配"，是这几种写法

1. **hook 点选错（头号风险）**：hook 到 `View.draw` / `TextView.setText` 这类高频方法，
   刷列表时每秒几十上百次回调 —— 电就是这么没的。
   → 硬约束：只 hook 低频入口（页面启动、控件出现、布局完成），回调里**先做最便宜的判断**
   （包名/页面名不对立刻返回），再加冷却窗口与次数上限。
2. **定时轮询 / 延时任务**：一律禁止。事件驱动，不做任何"每隔几秒看一眼"。
3. **命中记录频繁写磁盘**（S5 那条需求）：必须内存缓冲 + 批量落盘 + 限流，
   否则"记录"本身变成耗电大户（旧实现反过来踩过：没定时兜底导致数据发不出去）。
4. **hook 网络读写层**：每次网络读写都过一遍规则 = 灾难。架构里已经排除了（不做 Socket/BlockGuardOs 层）。
5. **无障碍服务常驻不待机**：装了框架就必须自动待机（旧实现实测过：接管后无障碍零命中）。
6. **订阅后台自动更新**：不做，只手动一键导入 —— 省掉一个常驻联网唤醒源。

### 8.4 怎么验（S8 的口径）

`dumpsys batterystats --reset` → 正常用 24 小时 → 导出对比，
同时看：**零 WakeLock、零常驻服务、零轮询**（这三个是机制层面的前提，比电量数字更早能验）。

## 九、AI 生成规则：设计方案

**底线（沿用旧实现已经验证过的）**：没填接口时整条链路照常可用，AI 只是加分项。

### 9.1 关键设计：模型不写规则，只做判断

这是旧实现踩过又改对的一条，必须保留：

```
第一段（模型）：给判断，不给规则
   输入：裁剪过的上下文（~300 token）
   输出：{ "是广告吗": true, "该做什么": "藏掉", "把握": 0.8, "理由": "…", "动哪个": "自己|往上两层" }

第二段（本地）：判断 → 规则
   选择器（怎么找到它）永远由本地代码生成
```

好处很实在：**模型再怎么胡说，也生不出一条非法规则**（它最多给错动作，本地翻译成规则时校验会挡住）。

### 9.2 三个入口（按性价比排序）

| # | 场景 | 触发 | 成本 | 说明 |
|---|---|---|---|---|
| **A1** | **抓控件时给建议**（主入口） | 检视层选中控件 →「问 AI」 | ~300 token | 你已经指着具体东西问了，最准 |
| **A2** | **排错时解释**（新增，配你的命中记录需求） | 规则详情 →「为什么没命中」 | ~300 token | 本地先解释，解释不清再问 AI |
| **A3** | 整页兜底 | 抓整页 → 让 AI 猜 | ~1500 token | 最贵最不准，入口放二级，标"较贵较慢" |

A2 是你这轮新需求（"功能不正常要知道动哪条"）的自然延伸：
本地能解释的（比如"这条规则要找的文字已经变了"）就不花钱，解释不清才问。

### 9.3 花钱与隐私的硬规矩

- **默认完全不联网**，点了才发。
- 发之前**显示要发什么**（控件文字可能带隐私内容），批量问要**二次确认 + 可取消**。
- 并发限流 3，**超时 30 秒**（120 秒对用户等于卡死）。
- 接口填你自己的（沿用旧实现：不填也不影响任何本地功能）。

## 九之二、自动分析：实测结论（**能不能做，用两个真 App 试过了**）

> 原型：`tools/apk_analyze_demo.py`（扫 Manifest 的组件清单，按类名驼峰拆词 + 已知 SDK 路径判定）。

### 实测数据

| App | 组件总数 | 挖出候选 | 其中真广告 | 误伤/需谨慎 |
|---|---:|---:|---:|---|
| 美团 12.44.203 | 589 | 15 | GDT 的 `ADActivity`/`Rewardvideo*ADActivity`/`DialogActivity`、贝斯广告 `com.beizi.ad.*`、`MGBAdMainActivity`、开屏广告页 `MSVSplashAdActivity` 等约 12 条 | 3 条是 SDK 基础设施（`GDTFileProvider`、两个 `DownloadService`） |
| 懂车帝 | 1070 | 17 | `SplashAdActivity`（开屏）、`AdFullscreenActivity`、`AdBrowserActivity`、`AdsAppActivity`、`AdBannerLandingPageActivity` 等约 14 条 | 3 条是通知横幅（`com.bytedance.notification.*BannerActivity`，不是广告） |

**准确率约 80%**（"广告展示页"这一层），而且挖出来的东西质量不低 ——
GDT 那几个 Activity 就是标准的横屏/竖屏/激励视频/插屏广告页。

### 第一版踩的坑（值得记下来）

第一版用「大厂包名前缀」当广告特征（比如看到 `com.bytedance` 就当 SDK），
结果**懂车帝自己 200 多个业务页面全被判成广告**（IM 聊天、会员列表……）——
字节系 App 的业务代码本来就住在 `com.bytedance` 下面。
改成**只认广告 SDK 的确切路径**（`com.qq.e.`、`com.beizi.ad`、`/openadsdk/`、`pangle`…）之后，
候选从 291 条降到 17 条。

### 结论：能做，但只能做一半，且必须你确认

**能覆盖的**：广告页 / 广告落地页 / 广告 SDK —— 也就是 L0 那一层（组件级、SDK 级）。
**覆盖不到的**：信息流里的广告卡片。它不是组件，是普通控件，**静态分析完全看不见** ——
这部分只能靠手动抓或 AI。

所以定位是**候选推荐器**，不是自动生效：

- 扫 APK → 给出 10~20 条候选，每条带**置信度和理由**（"类名含 Ad" / "命中优量汇 SDK 路径"）
- **区分「广告展示页」和「SDK 基础设施」** —— 后者（文件提供者、下载服务）拦了会让 SDK 异常，
  单独一档且明确标风险
- 排除语境误伤：`.notification.`、`.im.`、`.chat.` 这类路径下的 Banner 不是广告
- **你勾选后生成规则，默认关**（归入风险级，见第四节 S4）

### 因此最终是三条路并存

| 路 | 覆盖 | 谁来做 |
|---|---|---|
| **订阅导入** | 大部分（控件类广告） | 社区规则，一键导入更新 |
| **自动分析候选** | 广告页 / SDK（L0） | 本地扫 APK，你勾选确认 |
| **手动抓 + AI 建议** | 订阅和自动分析都漏掉的 | 你指一下，AI 帮忙判断 |

## 九之三、隐藏整个入口（例：美团底栏的「视频」标签）

**结论：好做，兼容性风险低，纳入本版一起做。**

### 为什么好做

1. **美团底栏是原生 View**：上一节普查过，美团没有 Compose / Flutter（RN 也只有极少痕迹），
   底栏在进程内是能看见的真实控件树 —— 这是能做的**前提**，换成懂车帝那种 Lynx 界面就难说了。
2. **动作已经存在**：就是 `HIDE`（设成 GONE + 尺寸归零），不需要新增能力。
3. **定位方式现成**：底栏标签一般带文案（"视频"）或资源 id，用选择器 `[text="视频"]` 就能定位；
   要藏的是"整个入口"而不是那个图标本身，所以再往上一层取它的容器 —— 选择器用 `@` 标记目标，
   写法是 **`[text="视频"] > @LinearLayout`**（关系方向按 GKD 源码语义：`A > B` 表示 B 是 A 的祖先，
   即从找到的节点往上找容器；`@` 标在容器那段上表示"动它"）。
4. **隐藏比摘除安全**（你说的对）：GONE 不改变父容器的子元素结构，只是不显示；
   万一选错容器，**改回可见就恢复了**，不像摘除那样可能破坏布局索引。

### 风险与对策

| 风险 | 对策 |
|---|---|
| 选错了容器 → 把半屏甚至整页藏了 | 抓控件时**先高亮预览**再确认；隐藏后在该规则上留开关，一键恢复 |
| App 内部仍认为有 5 个 tab（选中态错位） | 真机验一次美团：藏掉视频 tab 后，其余四个 tab 切换是否正常 |
| App 改版后文案或 id 变了 → 隐藏失效 | 走降级链（资源名 → 文案 → 类名）+ 失效可见（需求第五节第 6 条） |

### 验收

真机美团：底栏只剩四个入口、视频相关内容不再出现、其余 tab 正常切换、App 不崩。
这条同时是 S2（HIDE 动作）和 S7（检视层选父容器）的验收用例。

## 十、菜单：如果重新设计，我会改这一处（**备选，不阻塞开工**）

主方案（第二节）照常先用。但有一处我觉得可以更好：

**现在**：应用详情里规则按**来源**分两栏（我抓的 / 订阅来的）。
**备选**：按**广告类型**分（开屏 / 信息流 / 弹窗 / 摇一摇），来源降成一个小标签，顶部给个"按来源"切换。

理由：上次调研 GKD 时得出的一条结论 —— **分类要按"用户想关掉什么"，而不是"用什么机制/从哪来"**。
你心里想的是"别让开屏广告烦我"，不是"我要改一条订阅规则"。
来源分组对**排错**更顺手（我抓的优先级最高，要能一眼找到），所以它保留成可切换的视图。

另外看板可以考虑加一栏"**最近处理了什么**"（按时间倒序的命中记录）——
排错时这是最快的一条路，比从应用列表一层层点进去快。
